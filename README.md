# ReconProof

Financial reconciliation that automates only what it can prove, and accounts for
every rupee it cannot.

Orders, payments, refunds, fees, settlements and bank credits rarely agree.
References go missing, banks truncate them, settlements aggregate hundreds of
payments, refunds land in a later window, webhooks arrive twice, and a rupees
column occasionally gets read as paise. ReconProof resolves what the evidence
establishes, withholds what it does not, and itemises the difference.

Built for the [Razorpay AI Buildathon](https://razorpay.com/buildathon/) — AI
Finance Controller track.

---

## Quick start

Requires Python 3.12 and Node 20+. No Docker, no database server, no API key, no
GPU, no network access after install.

```bash
make setup     # virtualenv + npm install
make demo      # generate data, fit, calibrate, reconcile, analyze (~60s)
make api       # terminal 1
make web       # terminal 2 → http://127.0.0.1:43917
```

`make demo` is fully seeded. The numbers below reproduce exactly.

## What it does

```
Source files (7)
   │
   ├─ validate ──────── structural fault rejects the whole file; an isolated bad
   │                    row is rejected and itemised
   ├─ normalize ─────── canonical entities, integer paise, comparable references
   │
   ├─ exact match ───── shared identifiers, plus the fee report as a bridge for
   │                    the payment→settlement link neither file states
   │
   ├─ subset attribution ── refunds resolved against each settlement's reported
   │                        refund total by exact subset-sum
   │
   ├─ candidate generation ── only for what remains, blocked on amount and date
   ├─ calibrated scoring ──── per-relation thresholds with a proven risk bound
   ├─ global assignment ───── competing claims resolved as an assignment problem
   ├─ pairwise invariants ─── vetoes anything financially impossible
   ├─ settlement balance ──── re-checks each settlement's full allocation set
   │
   ├─→ reconciled ledger   (auto-accepted)
   └─→ exception queue     (with evidence, counterfactuals and an audit trail)
```

Everything the pipeline could not prove goes to the queue, where a bounded
investigation agent gathers evidence and proposes a resolution for a human to
approve or override.

## Measured results

Held-out dataset, 3,110 records across 7 sources, seed 2002. Generated by
`make demo`; the full report is at
`.reconproof/artifacts/evaluation_report.json`.

| Metric | Result |
|---|---|
| Match precision | **1.0000** (0 false positives) |
| Match recall | **0.9918** |
| Automatic match rate | **98.2%** |
| Settlement value traced to a bank credit | **84.7%** |
| Settlements balancing exactly | **96 / 98** |
| Unexplained value represented in the queue | **100%** |
| Links rejected by an accounting invariant | 15 |
| Runtime | ~3.0s |

Thresholds are calibrated per relation against a Wilson lower bound on
precision:

| Relation | Threshold | Proven precision bound | Calibration rows |
|---|---|---|---|
| `order_to_payment` | 0.005 | ≥ 99.84% | 29,834 |
| `settlement_to_bank_credit` | 0.899 | ≥ 99.02% | 764 |

### Compared against baselines

The model is reported next to what simpler approaches already achieve, because a
learned model that cannot beat a rule is not worth its complexity.

| Approach | Precision | Recall |
|---|---|---|
| Exact reference only | 0.500 | 0.008 |
| Amount + date window rule | 0.865 | 0.910 |
| Hand-weighted heuristic | 0.992 | 0.910 |
| **Calibrated model** | **1.000** | **0.992** |

### What remains unresolved, and why

The 15.3% of settlement value that does not trace is not a failure — it is
correctly withheld. It consists of seeded missing bank credits, credits arriving
days late, settlements whose fee lines disagree with the schedule, payments in
the wrong currency, and paise/rupee errors. Each appears in the queue with its
amount and cause.

## Design decisions

### Money is never a float

Every amount is an integer count of the currency's minor unit.
`Money.from_major(0.07)` raises rather than silently accepting a value binary
floating point cannot represent. Rate arithmetic uses `Decimal` with an explicit
rounding mode and collapses straight back to an integer.

This is what lets the settlement-balance check be exact equality. With a
tolerance, real breaks could hide inside it.

### Automation is gated on a proven bound, not a probability

A model saying `0.99` says nothing about how often *the accepted set as a whole*
is wrong. So each threshold is chosen on held-out calibration data using a
one-sided Wilson lower bound on precision — conformal risk control in the
Learn-then-Test sense.

The practical consequence is deliberate: a small calibration set produces a
conservative threshold, and a relation whose bound cannot reach the target keeps
automation **off** rather than running at an unproven level. Automating less on
thin evidence is the correct behaviour.

### Fitting and calibration use different distributions

The fitting dataset is augmented with extra truncated references, typos and
same-amount decoys, because the model needs to see hard cases often enough to
learn from them.

Calibration deliberately does not use that distribution. A risk bound measured on
adversarially hard data does not transfer to production. Thresholds are
calibrated on a separate dataset with realistic corruption rates, and a third
held-out dataset produces every reported number. Three datasets, three seeds, one
job each.

### Refund attribution is arithmetic, not inference

A settlement reports the *total* refunds it absorbed, never which refunds those
were. Scoring refund/settlement pairs independently reached **18% precision** —
a refund's amount and date are equally consistent with any batch that has room
for it.

But the aggregate is exact, so the question is not "does this look right" but
"which subset sums to exactly this total". That has three genuinely different
answers, and saying which one occurred is more useful than a confidence score:

- **one subset** — determined, not estimated
- **several subsets** — proven ambiguity, so a human decides
- **no subset** — a record is missing or an amount is wrong

This collapsed 989 low-confidence candidates to 14 and raised balancing
settlements from 36/92 to 96/98.

### Where AI is used, and where it is deliberately not

| Layer | Approach | Why |
|---|---|---|
| Identifier matching | Deterministic | An identifier is proof, not evidence |
| Refund attribution | Exact subset-sum | The aggregate is exact |
| Ambiguous matching | Calibrated logistic regression | Genuinely uncertain; coefficients map to interpretable features |
| Acceptance decision | Policy over a proven risk bound | A model must not set its own tolerance |
| Ledger arithmetic | Integer, deterministic | Never a model's job |
| Exception investigation | Bounded agent | Unstructured judgement over gathered evidence |
| Verification | Deterministic | The agent proposes; this decides |

Logistic regression over gradient boosting was chosen so counterfactual
explanations stay faithful to what the model actually did. The evaluation reports
both, so the choice is defended with numbers rather than asserted.

### The agent proposes; it never decides

Its authority is bounded by its tool surface rather than by its prompt: nine
read-only, row-capped, policy-authorized tools. There is no tool that executes
SQL, writes a record, changes a threshold, reads the filesystem or posts a match.
Denied calls are recorded rather than dropped, since reaching for a forbidden
tool is itself a safety signal.

Every proposal passes a deterministic verifier that:

1. looks up each cited evidence id in the database
2. confirms the candidate involves the exception's subject
3. recomputes the allocation from the records
4. re-runs every accounting invariant
5. enforces the policy's floor on *verified* citations only

A fabricated citation fails the recommendation instead of persuading a reviewer.
That specific failure is what makes AI unusable in finance, so it is checked
rather than trusted.

**Written as an explicit state machine, not with LangGraph.** What this workflow
needs is a persisted step log, a hard tool budget and a verifier that can veto
the model; a framework would add orchestration sugar over eight fixed transitions
without supplying any of the three. Each phase transition is already an
`agent_steps` row, which is the checkpointing an audit replay actually uses.

### It runs with no language model at all

The deterministic provider is the default, not a stub. It completes all seven
investigation phases on rules alone, which is what demonstrates that
reconciliation correctness never depended on a model being present. It is also
the control when scoring an LLM's contribution.

Ollama is used automatically when reachable, and an Anthropic key enables a
hosted provider. All three implement the same interface and pass through the same
verifier, so the set of things the system will accept does not change with the
model.

### Failure is designed for, not patched around

| Scenario | Behaviour |
|---|---|
| Changed export format | Structural fault; nothing imported, batch untouched |
| One malformed row | Row rejected and itemised; the amount stays attributable |
| Byte-identical re-upload | Recognised and ignored, recorded in the audit log |
| Replayed webhook | Collapses on its natural key |
| Ambiguous match | Withheld; both candidates shown with their evidence |
| Settlement won't balance | Every accepted link in it demoted to review |
| Date-only timestamp | Ordering tolerance widens; nothing asserted the source didn't say |
| Prompt injection in narration | Quoted inertly and flagged to the agent |
| Model unreachable | Falls back to rules; reconciliation unaffected |
| Distribution drift | Risk budget **tightens**; never loosens |

### Drift can only tighten

A threshold's guarantee was established on a particular input distribution. When
the inputs move, that evidence is less applicable, so the honest response is to
automate less until it is re-established. A drift detector able to *increase*
automation would be a mechanism for silently voiding the guarantee it exists to
protect.

## Architecture

```
apps/api/reconproof/
  domain/         Money (integer minor units), canonical entities
  ingest/         Parsers, column mapping, atomic loader, dedupe keys
  matching/       Exact, subset-sum, candidates, features, scoring, assignment
  accounting/     Pairwise and aggregate invariants
  policy/         Versioned policy engine and agent budgets
  agent/          Tools, providers, verifier, investigation state machine
  learning/       Labeling, training harness, active-learning store
  monitoring/     Anomaly detection, drift, batch briefing
  audit/          Append-only log
  api/            FastAPI routes and response models

apps/web/src/
  app/            Dashboard, batch views, exception review workspace
  components/     UI primitives, agent trace, evidence graph
  lib/            Typed API client, formatting
```

**Stack:** Python 3.12, FastAPI, SQLAlchemy 2, SQLite, scikit-learn, NetworkX,
SciPy, RapidFuzz, Polars · Next.js 16, TypeScript, Tailwind 4 · pytest,
Hypothesis.

SQLite is the default so a reviewer can clone and run with zero infrastructure.
The schema and every query are engine-portable; point `RECONPROOF_DATABASE_URL`
at PostgreSQL to switch.

## Tests

```bash
make test    # pytest; includes promotion-gate and ingest API tests
```

The suite asserts the claims rather than the implementation:

- no unexplained value escapes the exception queue
- no accepted match violates an invariant
- two runs of the same input agree exactly
- a duplicate upload cannot move a balance
- a settlement's balance identity closes at any scale (property test)
- a genuine subset is never missed (property test)
- money arithmetic is exact across generated inputs (property test)

## Data and honesty

All data is synthetic and generated from a seed. The generator builds a
*correct* ledger and records its ground-truth links first, then corrupts only the
surface form, tagging each corruption so evaluation can report per-corruption
performance instead of hiding weak spots in an average.

Amounts are drawn mostly from a catalogue of common price points, because real
merchants sell the same SKUs repeatedly and identical amounts are the norm. A
continuous distribution would make "same amount within the window" a near-perfect
matching rule and turn the reported precision into a property of the generator
rather than of the matcher.

**No figure in this repository is a real merchant result.** Every number is
measured on seeded synthetic data and reproducible with `make demo`.

## Configuration

All optional; every default works offline.

| Variable | Default | Purpose |
|---|---|---|
| `RECONPROOF_DATABASE_URL` | SQLite in `.reconproof/` | Point at PostgreSQL to switch engines |
| `RECONPROOF_TARGET_PRECISION` | `0.99` | Precision the thresholds must prove |
| `RECONPROOF_RISK_BUDGET` | `0.01` | Maximum permitted error probability |
| `RECONPROOF_LLM_PROVIDER` | `auto` | `auto`, `ollama`, `anthropic`, `deterministic` |
| `RECONPROOF_OLLAMA_MODEL` | `qwen3:4b` | Local model tag |
| `RECONPROOF_ANTHROPIC_API_KEY` | unset | Enables the hosted provider |
| `RECONPROOF_ENABLE_SEMANTIC_MATCHING` | `false` | Sentence-transformer features (extra install) |
